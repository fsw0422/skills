# write-as-me

Drafts must read like the user wrote them, not like AI output. The voice comes from a private profile on the user's machine. This skill holds only the workflow and defaults.

## Profile (private, local)

Location: `$WRITE_AS_ME_DIR` if set, otherwise `~/.config/write-as-me/`.

- `style-guide.md`: identity, personal hard rules, voice, registers, investigation shape, phrases, avoid list.
- `examples.md`: paraphrased example messages per situation and register.

Read both before the first draft in a session. Profile rules override the defaults below. The hard rules always apply.

If the profile directory is a Git repository, run `git pull --ff-only` there before reading it, so updates made on other machines are picked up. If the pull fails (offline, diverged), say so and use the local copy.

The profile describes a real person and often their workplace. Never copy its content into this repository, a commit, a PR, an issue, or anywhere public.

No profile yet: if the user keeps it in a private Git repository, clone that into the profile directory. Otherwise offer to build one with `references/building-a-profile.md`, then save it using `references/profile-template.md`.

## Hard rules (always)

- Never post or send without an explicit OK from the user in this conversation.
- Never frame the text as AI output ("Claude / AI found...", "Generated by..."). Findings are stated as the user's own.
- No secrets, tokens, or credentials.
- No personal data about customers or third parties beyond what the thread already has and the reply needs.
- No profanity or crude wording.

## Defaults (the profile may override)

- No em dashes, markdown headers, bold, or tables: they read as AI output. Code and logs go in fenced blocks.
- As short as the content allows. No intro restating the question, no stock closers ("I hope this helps", "Let me know if you have any questions").
- At most one hedge ("I think" / "seems") and at most one emoji per message.
- Register: slightly formal for internal audiences, formal for external ones.
- Investigation / incident write-ups: a conclusion line, 2-4 short bullets in plain words (what happened, how bad, whether it's over), then one next step. No exception, class or method names.

## Workflow

1. **Load the profile.** If it's missing, see above.
2. **Read the context.** For a thread or channel link, read it: who is asking, what has been said, what is being asked of the user. For investigation write-ups, use the findings from the current session.
3. **Classify the audience.**
   - Internal casual: the user's own team, teammate DMs, their manager.
   - Internal cross-team: other teams, support, on-call, incident channels.
   - External: customers, vendors, partners, shared or cross-company channels, or anything the reader will relay to a customer verbatim.
4. **Pick the register** from the profile (or the default above).
5. **Write the draft** following the profile. Investigation and incident write-ups follow the profile's investigation shape.
6. **Self-check** before saving: profile rules, hard rules, defaults, and the profile's avoid list.
7. **Output.**
   - Slack target: save it with the Slack connector's draft tool (e.g. `slack_send_message_draft`, passing `thread_ts` for thread replies) so the user only has to review and press send. Never use the send tool for drafts.
   - One draft per target. A redraft overwrites it by saving to the same channel and thread. Never spread versions across other channels, DMs or threads.
   - Don't paste the draft into the chat. Reply with one line naming the target, the register, and the channel link, plus any caveat the user needs before sending (e.g. an unverified fact).
   - No target yet: ask for the thread or channel link.
   - `draft_already_exists`: ask the user to clear the existing draft, then retry. Show the text in chat only if they ask.
   - Non-Slack targets (tickets, docs): show the draft in chat for the user to paste.

## Feedback loop

When the user edits a draft, rejects a phrase, or says they wouldn't write it that way, update the profile files (adjust a rule, add to the avoid list, or add the corrected message to `examples.md`) and tell them what changed. Edit only the profile directory: never the installed plugin files, which are replaced on update, and never this repository.

If the profile directory is a Git repository, commit each update right away with a short message saying what changed (e.g. `Avoid "circle back"`), then push it. Before the first push in a session, confirm the remote is private (e.g. `gh repo view --json visibility`). If it's public or can't be confirmed, keep the commit local, don't push, and tell the user. Report a failed push.

Keep the profile free of third parties' names, customer details, and secrets.

To recalibrate from fresh messages, rerun `references/building-a-profile.md` and merge the result into the existing profile.
